# 2026-11-17 前後台效能診斷與修正

## 範圍與證據邊界

使用者反映前後台偶發卡頓、內容無法出現、匯入名單與賽事操作等待。此次依現行原始碼、production build、元件回歸測試與本機預覽確認額外請求及載入阻塞；沒有在正式資料上大量匯入或修改比分，也未量測使用者當時的裝置、網路與 Firestore 正式交易延遲。因此下列是已確認的程式問題與改善，不能宣稱已找出每次卡頓的唯一根因或實際秒數改善。

公開品牌 Logo 改為非互動 div，保留原圖、尺寸、替代文字及返回系列賽連結。點擊 Logo 不再清掉 event/series 參數返回首頁。

## 確認的問題與實作

### 1. CSV 匯入產生多餘的全表讀取與逐筆賽事交易

原先每列皆依序 `saveIdentity` → `onPlayer`，後者寫入整份賽事文件。每次 `saveIdentity` 完成又觸發所有私人選手訂閱執行 `getDocs(privatePlayers)`。32 人匯入除了 32 次必要的身分 transaction，還會有 32 次賽事 transaction 與 32 次額外私人名單全表讀取；網路往返延遲會累加。

現在儲存成功後，只將該筆私人 profile 合併至後台訂閱的記憶體資料，不重新下載整表。初次開啟與視窗取得焦點仍查詢伺服器；同一訂閱查詢進行中會合併重複的 focus 請求，並保留查詢期間新儲存的資料，避免晚到的讀取覆蓋剛儲存的 profile。取消訂閱會解除事件及通知。私人資料不寫入 localStorage、持久快取或公開賽事；`saveIdentity` 對外仍只回傳 id/name。

一般積分賽／合作賽報名新增 `onPlayers`：每 8 位提交一次賽事 transaction；不足 8 位或遇到須人工核對的身分時先提交前段。32 人正常匯入的賽事交易由 32 次降為 4 次（減少 87.5%），匯入後額外整表讀取由 32 次降為 0 次。身分交易仍逐筆核對索引與版本，避免平行寫入造成重複身分。最終戰單一資格席位維持逐筆處理。

僅在賽事交易成功後才移除待處理列。失敗批次保留供重試，已完成批次不重送；私人 profile 可能已保存但尚未加入該場，這是兩個獨立交易的既有邊界，重試仍會重新核對身分。顯示已完成／總筆數。每批新增選手仍經過 `registeredPlayers` 的人數與重複檢查、latest revision 檢查和既有 audit transaction。

### 2. 後台列表被伺服器摘要檢查阻塞

原先必須等 `ensureTournamentSummaries` 的 server-only 讀取完成才建立 `subscribeAdminTournaments`。即使已有可顯示的摘要，慢網路也會延後整個列表；檢查失敗時甚至不會開始訂閱。

現在直接啟動摘要訂閱，同時背景檢查／補齊摘要，保留錯誤提示。資料遷移或檢查不再是顯示列表的前置依賴。沒有取消摘要補齊，也沒有掃描整份賽事作為每次列表載入的替代方案。

### 3. 公開系列 metadata 更新造成清空與重訂閱

原先場次 effect 依賴 `series.events` 陣列參照；Firestore 每次傳回新的 document 物件，即使場次相同，也可能先清空 `tournamentsByCode`，取消並重建全部場次訂閱，造成短暫空白和重算。

現在以場次代碼序列作為依賴。metadata、系列名稱或場次標籤更新仍正常顯示，但不清空賽況、不重建訂閱。代碼或順序實際改變、手動重試時仍會正確重建。

### 4. 公開入口下載後台程式

原先 `main.jsx` 直接載入含完整後台的 `App.jsx`，公開觀眾也下載後台表單、QR code 等。新增小型 `AppRouter.jsx` 作為入口，只在 `?admin` 動態載入後台，保留既有路由、管理權限檢查及原 App 的具名匯出。

同一套依賴 production build 比較：

| 指標 | 修正前 | 修正後 |
| --- | ---: | ---: |
| 公開入口初始 JavaScript，未 gzip | 1,001.19 KB | 約 888.37 KB |
| 公開入口初始 JavaScript，gzip | 298.77 KB | 約 269.81 KB |
| 後台主分包，僅管理入口載入 | 與公開入口合併 | 111.08 KB / gzip 33.05 KB |

修正後數字合計公開 HTML 的 entry/modulepreload 分包，非只看 entry 檔案。gzip 約減少 9.7%；Firestore 等共享依賴仍是主要體積，因此尚有大於 500 KB 的共享 chunk 警告。沒有宣稱此分包能修好雲端交易延遲。

## 賽事操作仍可能等待的原因及下一步

- SeasonAdmin 的一般比分、輪次、棄賽等操作使用 transaction 確認 revision 後才更新，期間停用操作；這段等待包含雲端往返與競爭重試。舊制後台另有 400 ms 合併儲存延遲和網路失敗重試。未改成提前宣告成功，以保留多裝置衝突及完賽鎖定保護。
- `pairEvenGroup` 已有 5,000 搜尋節點上限；本次未取得 CPU profile 證據顯示瑞士配對或排名是嚴重卡頓主因，因此不更動配對、排名規則或加上 Web Worker。
- 正式環境下一步應以發生問題的手機記錄 Network/Performance：分別量測身分交易、賽事交易、首次 snapshot、長任務、斷線及重試時間，區別主執行緒停頓與網路等待。
- 確認 Firestore 實際資料庫地區是否接近台灣使用者；尚未查證正式地區，不建議直接搬遷。
- 檢查 `players`、`rounds`、`bracket` 等不作查詢的大型陣列／map 是否仍使用預設自動索引。若有，評估單欄索引豁免以減少寫入負擔；本次沒有部署任何索引或資料庫設定變更。後續規模增加時可再評估按對戰拆文件，但這是架構變更，需要另行規劃。
- 初次私人名單載入仍為整表讀取；本次消除匯入時的重複下載。若名錄成長到明顯影響首次開啟，應另做伺服器索引查詢及按需載入，保留本名／電話雙索引核對。

官方參考：[Firestore 最佳實務](https://firebase.google.com/docs/firestore/best-practices)、[交易及批次寫入](https://firebase.google.com/docs/firestore/manage-data/transactions)。官方亦說明網路距離、索引負擔與交易競爭都影響延遲；這些是後續查證方向，並非已量測的正式站根因。

## 驗證

- 160 項應用測試、production build、`git diff --check` 通過。
- 元件回歸涵蓋 32 人分四批提交、失敗只重試未完成批次、身分衝突前先提交前段、單筆資格席位、私人資料不進公開寫入。
- 私人名單測試覆蓋儲存不再全表讀取、重複 focus 合併、晚到 server read 與本地更新合併、取消訂閱。
- 公開系列測試覆蓋 metadata／名稱更新保留資料與訂閱、增加場次仍訂閱；Logo 無連結也不可鍵盤聚焦。後台測試覆蓋摘要檢查 pending 時仍立即訂閱列表。
- 本機虛構第二輪預覽正常顯示，實際點擊 Logo 後 URL 與頁面內容保持；未操作正式賽事資料。
- Firestore 整合／權限測試 16 項通過；因預設 8080 被其他工作占用，使用獨立 8187 模擬器與 Node 24 執行，沒有干擾既有模擬器。
- Impeccable 機械檢查無發現。手機硬體、Safari 與正式網路延遲未量測。
