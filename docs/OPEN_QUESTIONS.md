# 待確認的核心設計問題

依 `AGENTS.md` 的要求，以下問題會影響核心架構或比賽結果；確認前不擅自選定方案。

## 賽制規則

1. 單場固定三輪，還是應依參賽人數自動／手動設定輪數？ 
固定三輪
2. 後續配對是否必須避免同一對手重複交手？若無法完全避免，優先順序為何？
是，要避免。如果真的同分的只剩這個組合，那就照樣打
3. 奇數人數的 MC 對戰是否正式計入勝場與票數？MC 由誰擔任，且同一選手可否多次對上 MC？
MC不是一個真實存在的選手，只是為了避免輪空問題抓他下去打。因此由誰擔任不重要（比賽現場處理，無關系統），但要避免多次對到，然後與MC對戰的人計入戰績
4. 目前排名依「勝場、總票數」排序；是否還需要對手分、Buchholz、勝負關係或加賽作為破同分規則？
要，排列順序為：勝場 => 總票數 => 對手勝率 => 對手的對手勝率 => 加賽
5. 棄賽前已完成的成績是否保留？未完成對戰應重抽、判負，或取消？
保留，棄賽的該輪直接判敗

## Phase 2：後端與前後台

1. 後端、資料庫與部署平台是否已有偏好或既有帳號／預算限制？
我偏向使用google firebase，且希望都使用免費功能
2. 後台管理員如何登入：單一共用帳號、Google 登入，或多位具不同權限的工作人員？
單一共用帳號（甚至不用到帳號密碼，只要一組token就夠了）
3. 是否需要比分修改歷程（操作者、時間、修改前後值）與不可刪除的稽核紀錄？
要
4. 公開前台使用不可猜測連結、賽事代碼或完整賽事列表？已結束賽事是否永久公開？
賽事代碼。永久公開，但可以從後台做開放關閉的調整
5. 即時更新可接受數秒輪詢，還是必須使用 WebSocket／Server-Sent Events？
都可以，但希望越快越好，且不需要refresh瀏覽器就能更新
6. 賽事現場網路中斷時，後台是否必須離線操作並在恢復後同步？
可以的話最好

## Phase 3：報名、選手與系列積分

1. 四場積分賽的積分公式為何：各名次、參賽、勝場或票數分別取得多少分？
2. 並列、棄賽、取消資格、缺席與補賽如何計算系列積分？是否取最佳幾站或四站全計？
3. 跨場次如何識別同一選手：Email、電話、社群帳號、會員編號，或人工確認？公開頁面可顯示哪些個資？
4. Google Form 的實際欄位、試算表格式與存取方式為何？採定時同步、手動匯入，還是 Apps Script 主動通知？
5. 重複報名、改名與資料衝突由系統自動合併，還是進入後台待人工確認？
6. 賽事結果何時鎖定並累積積分？鎖定後更正結果是否需要重新計算整季排行榜與保留版本？

## 建議優先確認

要開始 Phase 2，至少需先確認：後端／部署限制、管理員登入方式、公開賽事網址形式，以及前五項賽制規則。Phase 3 則至少需要正式積分公式、唯一選手識別方式與 Google Form 欄位範例。
